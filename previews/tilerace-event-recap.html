Tile Race - Event Recap

What /activities/tilerace renders once an event has ended and no other event is active or scheduled: submission graphs, position history, and final leaderboards built from that event's own data - with players removed during the event dropped from every count.

Mock data. Palette and type from web-app/styles/globals.css; team colours from api-backend/app/routers/tilerace/_teams_shape.py TEAM_COLORS. Charts drawn as inline SVG here; in the app they are recharts 2.15.4 via @/components/ui/chart, matching FrenzyRankChart.tsx.

How the page decides: GET /tilerace/active falls back to the newest finished event (events.py:80-88). The route reads that event as ended when is_finished is set or ends_at is in the past, fetches GET /tilerace/events/{id}/recap, and switches on recap.next_event: null means layout A, present means 3B.

4. Dropping removed participantsthe counting rule

A submission row keeps discord_user_id and player_rsn forever (TileRaceSubmission), but the roster row it came from can be deleted mid-event via DELETE /tilerace/events/{id}/roster/{discord_user_id}. The recap counts a participant only when a tilerace_signups row for them still exists at close.

Where the rule bites

SurfaceRemoved participant
Contributor leaderboardomitted entirely
Roster cardsomitted entirely
Team approved / rejected totalstheir tiles not counted
Tiles-submitted-per-day graphtheir tiles not counted
Team position historyunchanged - the team moved, and a roll is the team's
Tiles clearedunchanged - a cleared tile stays cleared
Event-level submitted countexcluded, and the delta is stated once ("3 removed participants excluded")
Consequence to accept: team approved totals and tiles cleared can disagree (a tile cleared by a since-removed participant is no longer in the team's approved total). The stat card footnote is what keeps that honest.

Where each number comes from

Recap elementSource tableReaches the browser via
Event name, dates, winner, finished, path length tilerace_events recap.event, filtered through PUBLIC_SUMMARY_KEYS
Final + furthest position, team colour, standings order tilerace_teamsrecap.teams[]
Position history over time tilerace_rollsteams[].position_series
Tiles cleared per team tilerace_tile_completions (claimed or approved) teams[].tiles_cleared
Submission counts, per team and per participant tilerace_submissions teams[].approved/rejected, teams[].roster[], teams[].submission_series
Which participants survived to close tilerace_signups rows still present never sent - the filter runs server-side, only the count of dropped authors ships as totals.removed_participants
Why it is aggregated server-side. The rows behind these numbers carry proof URLs, review notes, thread ids and Discord ids. Shipping counts and series instead means none of that can leak, the same discipline _public_view.py applies to the board - and it keeps the "removed participant" filter in one place, next to the roster it filters against.
