1. Shape of the system

Three processes and one datastore. No process calls another directly; everything meets in Valkey.

Why nothing calls anything directly. api-backend never holds a Lavalink player and discord-utils never holds a web request. The only thing crossing between them is an intent on a pubsub channel, and authority is re-checked on the receiving side. That is what makes "you must be in the voice channel" hold identically on both surfaces - neither can be talked into driving a channel nobody is sitting in.

2. Storage and contracts

Valkey keys

KeyTypeHolds
music:lease:{index}stringWhich channel holds player bot N.
music:session:{channel}hashCurrent track, paused, position, updated_at, volume, loop, shuffle, bot, channel name.
music:queue:{channel}listQueued tracks as JSON, in play order.
music:activity:{channel}list (cap 25)Who did what, newest first.
music:history:{channel}list (cap 100)What already played, newest first, audio stripped.
music:voice:{channel}setWho is in the channel - the "may control" answer.
music:commandspubsubWeb intent to the bot.
music:statepubsub"This channel moved" notice to the API.
music:eventsstreamPlayback events awaiting durable counting.

The five session keys share a 300s TTL, refreshed by the pool heartbeat. A killed bot publishes no closing notice, so silence is the only signal a session has gone - the TTL is the cleanup.

Pinned contracts

Two fixtures at the repo root are asserted from both sides, so a field renamed in one service fails a test rather than silently reading back as a default:

  • fixtures/music_bridge.json - the session hash, a stored track, a published command, a history entry, and the channel names.
  • fixtures/music_playlist.json - the playlist payload discord-utils parses with its own models.

Plus the generated pair: api-backend/openapi.json → web-app/src/api/schema.d.ts, regenerated whenever a schema moves.

Resolution: two distinct steps

Search runs when a user queues something. A bare query defaults to Spotify because Spotify results carry an ISRC, the only stable identity a song has across sources.

Playback resolution runs at play time, for every track holding metadata rather than audio - a Spotify track (its audio cannot be streamed by a bot) or anything restored from a saved playlist. Order tried:

  1. The track's own URL, when it has one and is not a mirrored source.
  2. The ISRC, quoted, hyphens stripped - LavaSrc strips them before the same query, and a hyphenated ISRC matches nothing.
  3. Title + author on YouTube, then SoundCloud.
Why resolve late. A 200-track playlist loads in one request instead of 200 searches, and a track nobody ever hears costs nothing. It also makes played_source a real observed value rather than a guess - LavaSrc normally mirrors Spotify server-side inside its own call and reports nothing back.

4. Flow: a web command

Browser                api-backend                 Valkey            discord-utils
   │                        │                          │                    │
   │ POST /commands         │                          │                    │
   │ {action, ...}          │                          │                    │
   ├───────────────────────▶│                          │                    │
   │                        │ validate CommandRequest  │                    │
   │                        │ (schema is the guard)    │                    │
   │                        │ PUBLISH music:commands   │                    │
   │                        ├─────────────────────────▶│                    │
   │  200 {accepted, N}     │                          ├───────────────────▶│
   │◀───────────────────────┤                          │                    │
   │                        │                          │      re-check: is actor
   │                        │                          │      in the voice channel?
   │                        │                          │                    │
   │                        │                          │      apply() ─▶ session
   │                        │                          │◀───────────────────┤
   │                        │                          │  PUBLISH music:state
   │   WS frame: session    │◀─────────────────────────┤                    │
   │◀───────────────────────┤  (API reads hash, shapes payload)              │

200 means published, not performed. Whether anything changed arrives over the socket - which is also why the response carries delivered_to, the subscriber count.

Authority is re-checked, never trusted. The publisher could be any process. The bridge asks the voice roster itself before applying, so the rule holds whichever surface the command came from.

5. Flow: state back to the browser

One WebSocket serves the whole page - the panel and the mini player share it. The progress bar is extrapolated, not polled.

  session hash stores:   position_ms = 42000
                         updated_at  = 1774000000.5   (float epoch)
                         paused      = false

  browser, each 1s tick:  shown = position_ms + (now - updated_at * 1000)
                          capped at length_ms, rounded to a whole ms
                          CSS transition (1s linear) fills the gap between ticks

  a state notice arrives ─▶ refetch ─▶ position and updated_at replaced
  • No server-side timer, no polling. A moving bar costs zero requests.
  • Rounded on purpose. updated_at is a float, so the extrapolation is fractional; a seek built from it was refused by the API, which takes an integer.
  • Queue and activity re-read on updated_at. A track queued from Discord moved the count on screen while the rows still showed whatever they held when the page opened.
  • 2.5 minutes of silence drops a session. A killed bot publishes no closing notice.

6. Flow: playback into stats

  history.record(track, PLAYED|SKIPPED, listened_ms)
        │
        ├──▶ LPUSH music:history:{channel}   (ephemeral, capped, audio stripped)
        │
        └──▶ XADD music:events               (durable intent)
                    │
                    ▼
  MusicStatsService.consume_once()  - own Valkey client, socket_timeout=None
        │
        │  XREADGROUP: pending "0" first, then new ">"
        ▼
    for each message:
        SET NX seen:{id}  ──▶ already claimed? skip, ack
        │ claimed
        ▼
        ON CONFLICT DO UPDATE  music_counters      (+= , JSONB source split merged)
        ON CONFLICT DO UPDATE  music_track_plays   (+= )
        │ failure ─▶ release claim, leave unacked
        ▼
        XACK

Stream, not pubsub

Playback never blocks on a database write, and a restart loses nothing that happened while it was down.

Claimed, not just grouped

A consumer group guarantees redelivery, not exactly-once. An inflated total is worse than a missing one because nothing can audit it back down.

Postgres does the arithmetic

Read-add-write in the consumer loses increments between two workers, and the whole point of a stream is that more than one may consume it.

Keyed on the recording

ISRC where a source gives one, else a digest of normalised title/author/duration. Keying on the source id lists one song once per source.

Counters carry a guild and a track and never a user id - so there is no per-member filter to forget on the way out. That is asserted against the response schema, not against a query.

8. Decisions worth remembering

The queue lives in Valkey, not in wavelink. wavelink's own queue is untouched and autoplay stays disabled, so the only thing deciding what plays next is advance. That keeps the queue the web reads and the queue Discord plays from as one object.
A carried cover beats a re-resolved one. Playback resolution finds a mirror of the recording on another source, and the mirror's art is not what the user picked from. The cover travels with the track through every write; the resolved one is only a fallback for a track that has none.
Names are stamped where the guild is in reach. api-backend cannot produce them - its users table only holds people who have logged into the website, and it stores a global username, never a server nickname. The browser certainly cannot. So discord-utils attaches the name on the way into the queue, once, and it travels with the record. The Discord panel keeps <@id> mentions, because there that is the resolved form.
enqueue is the single stamping point. Six surfaces reach it. Threading a name parameter through search_tracks, to_track and to_tracks instead would have touched every caller and their tests to reach the same place.
Discord ids cross as strings. A snowflake exceeds 253 and a browser parsing it as a JSON number rounds the last digits. The rounded id addresses a channel nobody is in, so every control silently read as forbidden and every playlist read as someone else's.
History is session state, not a record. A capped Valkey list under the session keys, so the heartbeat refreshes it and the orphan sweep removes it without either learning a new key. Persisting it would have been a per-guild play log - a different thing from the durable counters, and it would reopen the retention question the counters exist to close.
Re-queue needs no new command. A history entry carries the same metadata a search result does, so it travels back down the existing add path. A requeue action would have given one intent two implementations.
The panel shows ten, the website shows all. Ten is what fits in two rows of buttons beside a numbered list; paging the panel costs an edit per page for something nobody is watching.

9. Bugs found and fixed

The stats consumer counted nothing, silently. A blocking XREADGROUP occupies its socket for the whole block, and the shared request client is built with a far shorter socket timeout. Every poll timed out and the service sat in a permanent retry loop. Green in every test, because tests read non-blocking - it was visible only in the deployed stack's logs. Fixed with an owned client at socket_timeout=None; the regression test asserts the connection kwarg, since no functional test can catch this.
Seek did nothing at all. The extrapolated position is built from a float epoch, so position_ms arrived fractional and pydantic refused it - an integer field rejects a number with a fractional part. Rounded at both the source and the send site.
The volume slider was inert twice over. A Radix slider given value is fully controlled: without feeding the drag back, the thumb cannot move, and handleSlideEnd sees no change so onValueCommit never fires. Keyboard worked because that path commits from inside the state updater. Both sliders now feed their drag back into their own value.
A reorder deleted the cover. The web rewrites a playlist's whole track list to reorder or remove, so a field the browser forgot to carry was deleted from the table rather than left alone. Now pinned by an integration test.
Adding a key to the session set broke the heartbeat test. Adding HISTORY to SESSION_KEYS meant the refresh test's seeder never created it, and the TTL assertion read -2. The seeder creates it now - the failure was correct.
